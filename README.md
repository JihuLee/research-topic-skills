# research-topic-skills

[Korean](README.ko.md)

Agent Skills that **find, adversarially vet, and hand off** research topics for one researcher.

The same `SKILL.md` files work in Claude Code, Codex and other agents that support the [Agent Skills standard](https://agentskills.io/specification). The skills are generic. Each researcher's taste, budgets and history live in a separate **profile directory** that the skills read at run time.

## Install

Install with the [`skills` CLI](https://skills.sh/):

```bash
# list the skills in this repository without installing
npx skills add JihuLee/research-topic-skills --list

# install all three skills at user level (the CLI asks which agents to install to)
npx skills add JihuLee/research-topic-skills -g

# install a single skill
npx skills add JihuLee/research-topic-skills -g --skill novelty-gate

# update or remove later
npx skills update -g
npx skills remove -g novelty-gate
```

`topic-scout` hands its shortlist to `novelty-gate`, so install both if you use the scout.

The helper scripts need Python 3.8+ (standard library only). PDF text extraction uses pymupdf or pdftotext when either is available; otherwise PDFs are only saved.

## Design principles

1. **Verify more than you generate.** Ideas are cheap to produce. Topics usually die for one of three reasons:
   - a recent paper nobody looked for;
   - a classical result under another name;
   - a cheap baseline that already does the job.

   That is why `novelty-gate` is the core skill. Ideas generated by language models tend to look more novel before execution than after ([Si, Hashimoto & Yang 2025](https://arxiv.org/abs/2506.20803)).
2. **"None" is a normal result.** There is no quota of candidates.
3. **Kill only with evidence.**
   - A kill needs a named paper (URL and location) or a derivation the reader can check: a classical equivalence or a theory-forced result.
   - Search or access failures are never evidence of novelty.
   - "This area is crowded" is never a reason to kill by itself.
4. **Design falsification before experiments.** Every passing or near-miss candidate gets a B0, the cheapest experiment that could falsify it. Its thresholds are frozen with a hash before any result is seen. The skills design the B0; the researcher approves running it.
5. **Taste is data.** Preferences, exclusions, budgets, past topics with their killers, and owned assets live in profile files. To change behaviour, edit the files, not the prompts.

## Skills

| Skill | What it does | Main outputs |
|---|---|---|
| `novelty-gate` | Adversarially reviews an idea or proposal. It breaks the idea into claims and searches query families A–F for prior work. It verifies decisive quotes in full text and checks for classical equivalents and theory-forced results. It scores novelty and feasibility separately and designs a B0. | `gate_report.md`, `evidence.jsonl`, `thresholds.json` |
| `topic-scout` | Generates numbered candidates at a chosen level (high: from the researcher's own papers, code and notes; low: exploring recent literature in their field) and depth (quick, standard, full). It drops ideas only for objective reasons, then sends a shortlist to `novelty-gate`. | `candidates.jsonl`, `scout_report.md`, `corpus_manifest.md` or `landscape.md` |
| `research-brief` | Turns a passing candidate into an execution-ready specification for a human team or an autonomous research agent. It uses the researcher's own template if one is configured, inlines the literature facts, and freezes the threshold hash. | `brief.md`, `thresholds.json.sha256` |

```
corpus + profile + ledger ─► topic-scout ─► shortlist ─► novelty-gate ─► PASS ─► research-brief
                                  ▲                            │
                                  └─── ledger (killed / near-miss) ◄┘
```

`novelty-gate` also works on its own. Vetting an existing proposal is the most common use.

## Usage

Ask the agent, naming the skill or not:
- `Use novelty-gate on proposals/idea.md. profile: ~/research-profile`
- "Has anyone already done this? <idea>"
- "Read my paper and code in ./my-project and find follow-up topics."

In Claude Code you can also type `/novelty-gate …`. In Codex, type `$novelty-gate …`.

The skills look for the profile directory in this order:
1. A path given in the request.
2. The environment variable `RESEARCH_PROFILE_DIR`.
3. `./research-profile/` in the working directory.
4. `~/research-profile/` in the home directory.

If none is found, the skill asks four short questions once and creates one (see below).

To start a profile, copy [`templates/`](templates) from this repository:

```bash
cp -r templates ~/research-profile
mv ~/research-profile/ledger.example.jsonl ~/research-profile/ledger.jsonl   # delete the example lines
$EDITOR ~/research-profile/profile.md                                        # edit the json profile block
```

## Keeping the skills out of autonomous pipelines (guardrail)

These skills are for a researcher working with an agent, directly or through subagents that agent spawns for the request. They are not for autonomous research frameworks running stages unattended. Such runs follow their own frozen workflow, nobody is there to answer the approval questions the skills ask, and the skills would leave extra folders behind.

There are three layers of protection:
1. **Descriptions.** Every skill description ends with "For interactive use with a researcher, not for autonomous research pipelines." Agents read this when they choose a skill.
2. **First step.** Each `SKILL.md` has a "Who may use this skill" section. It tells the agent to run `scripts/guard.py` first, and to stop without doing anything when it runs as a pipeline stage.
3. **`guard.py`.** It exits with code 3 and prints a stop message when either of these holds:
   - `RESEARCH_TOPIC_SKILLS_DISABLE=1` (or `true`, `yes`, `on`) is set;
   - a sentinel file `.no-research-topic-skills` exists in the working directory or any parent.

   `RESEARCH_TOPIC_SKILLS_ALLOW=1` overrides both for a deliberate, supervised use.

For an autonomous framework, do one of these:
- add `export RESEARCH_TOPIC_SKILLS_DISABLE=1` to its launch environment;
- create `<workspace>/.no-research-topic-skills` at its workspace root.

The guard is cooperative: it relies on the agent following instructions. For hard isolation, run frameworks under a separate OS user, or install the skills at project level only.

## Finding topics: level and depth

Just ask; `topic-scout` turns your words into settings with `scripts/scout_settings.py` and shows them as a short card before it starts:

```
Find me a research topic.
Explore broadly and quickly, field: medical imaging.
Based on my code in ./my-project, thorough please.
```

```
level: low (request (phrase)) · depth: quick (request (phrase)) · gate: none (the user picks what to gate)
corpus: - (not used (level low))
direction: medical imaging · cutoff: 2026-11-04 · out: ./scout-2026-11-04-low
profile: ~/research-profile (found)
```

| level | Draws on | Phrases |
|---|---|---|
| high | mostly your own material: corpus, assets, ledger near-misses (80%) | "based on my code", "my paper", "follow-up" |
| medium (default) | half your material, half recent literature | (default) |
| low | recent literature only, matched to your field and taste; the corpus is never opened | "exploratory", "broadly", "just the field" |

| depth | Goes until | Phrases |
|---|---|---|
| quick | numbered candidates with quick novelty signals; you pick what to vet | "quick", "candidates only" |
| standard (default) | the top candidate vetted by `novelty-gate` in light mode | (default) |
| full | the top three vetted in full mode | "thorough", "in depth" |

- **Other languages:** Korean phrases are recognised too; see the Korean README.
- **Never affected by the level:** exclusions, budgets, the ground-truth policy, the ledger duplicate check, and the gate's standards.
- **Explicit settings:** you can state any of them directly, for example `level: low`, `depth: full`, `field: …`, `cutoff 2026-01-31`, `out: ./scout`, or a path to your material.
- **Profile defaults:** `scout_level`, `scout_depth` and `corpus_paths` in your profile.
- **Follow-ups:** candidates are numbered C1, C2, … and saved in `candidates.jsonl`, so you can continue with "gate C3" or "brief C1".
- **First use:** with no profile yet, the skill asks four short questions once (areas, exclusions, budget, language), creates `~/research-profile` with `scripts/profile_init.py`, and continues.

## Profile directory specification

```
<profile_dir>/
├── profile.md      # required: prose about taste + a json profile block of constants
├── ledger.jsonl    # recommended: past topics, verdicts and killers
├── lessons.md      # optional: checklist of recurring lessons
├── assets.md       # optional: owned datasets, weights, caches and tools
├── corpus/         # optional: input for topic-scout (or give paths in the request)
└── backtest/       # optional: private backtest cases and results
```

### `profile.md`

- **Prose:** what results excite you, your strengths (domains, instruments, data access), what you never want to work on again and why, and how you like to be told "no".
- **Constants:** exactly one fenced code block with the info string `json profile`. Scripts and skills read these values.

| Key | Type | Default | Used for |
|---|---|---|---|
| `output_language` | string (`en`, `ko`, …) | language of the request | report language |
| `interests` | list of strings, ranked | — | generation lenses, ranking |
| `preferred_contributions` | list (`method`, `benchmark`, `analysis`, `theory`, `dataset`) | `method`, `benchmark`, `analysis` | ranking |
| `target_venues` | list | — | framing and review criteria |
| `exclusions` | list | `[]` | dropped by the scout, flagged by the gate |
| `ground_truth_policy` | string | public, verifiable ground truth only; no human or LLM judgment as the primary metric | feasibility |
| `budgets` | object: `tiers` (per name: `gpu_hours`, `download_gb`), `wall_clock_hours`, `hardware` | — | feasibility, B0 cost |
| `novelty_entry_threshold` | int 1–5 | 4 | PASS / NEAR-MISS boundary |
| `recency_window_months` | int | 6 | recency sweep |
| `approval_required_for` | list (`downloads`, `experiments`, `gpu`) | all three | actions never taken without approval |
| `report_dir_pattern` | string with `{slug}`, `{date}` | `./gate-{slug}-{date}/` | output location (a directory named in the request wins) |
| `scout_level` | `high` / `medium` / `low` | `medium` | topic-scout: how much it draws on your own material |
| `scout_depth` | `quick` / `standard` / `full` | `standard` | topic-scout: candidates only / vet the top 1 (light) / vet the top 3 (full) |
| `corpus_paths` | list of paths | `[]` | topic-scout material when the request names none |
| `handoff_template` | path or `null` | `null` | your own template for research-brief |
| `content_check_command` | string or `null` | `null` | command research-brief runs on a brief before handoff (for example a secret scanner). It must not print the patterns it matches |

### `ledger.jsonl`

One JSON object per line. Validate with `scripts/ledger.py validate`. Write `title` and `claim` in English, even if your reports use another language: the similarity search compares words and character trigrams, so mixed languages do not match.

| Key | Required | Type |
|---|---|---|
| `id` | ✓ | string, unique |
| `date` | ✓ | `YYYY-MM-DD` |
| `title` | ✓ | string |
| `claim` | ✓ | one sentence |
| `verdict` | ✓ | `pass` / `near-miss` / `killed` / `dropped` / `closed` / `none` / `pending` |
| `stage` | | `idea` / `gate` / `b0` / `pilot` / `sealed` / `brief` / `done` |
| `novelty`, `feasibility` | | int 1–5 |
| `killers` | | `[{title, url, why}]`; for a derivation, omit `url` and say "runner derivation" in `title` |
| `near_miss_b0` | | the minimal evidence that would flip a near-miss |
| `tags`, `report`, `notes` | | list / path or URL / string |

```json
{"id": "2026-02-03-T2", "date": "2026-02-03", "title": "...", "claim": "...", "verdict": "near-miss", "stage": "gate", "novelty": 3, "feasibility": 5, "killers": [], "near_miss_b0": "...", "tags": ["uncertainty"], "report": "gate-.../gate_report.md"}
```

The ledger has two jobs:
- **Duplicate detection** (`ledger.py check`) for new ideas. A match with a past topic that has a named killer is a strong signal. It is not an automatic kill if the new idea says what changed.
- **History.** Verdicts accumulate through `ledger.py add --from-summary`, after you confirm them.

### `lessons.md`

Write each lesson as something checkable, for example "Check: the native, no-intervention pipeline is a registered baseline". `novelty-gate` applies every item as a checklist and reports the results in section 5 of its report. General starters are in [`templates/lessons.md`](templates/lessons.md).

### `assets.md`

Columns: `name | kind | path | size | license | provenance / training split | notes`. Used for feasibility scores and the owned-asset lens. For pretrained weights, always record the training split: it is how overlap with evaluation data gets caught.

### `corpus/`

Any files: papers (`.tex`, `.pdf`, `.md`), code repositories, notes, past gate reports. `corpus_scan.py` indexes where to look; the skill does the judging. It finds:
- theoretical compromises: assumptions, approximations, limitations;
- code-only tricks: clamps, detaches, epsilons, constants;
- heavy calls inside loops;
- past verdicts and lessons.

## Output specification

```
<out_dir>/
├── gate_report.md      # human-readable report ending with a gate-summary JSON block
├── evidence.jsonl      # evidence log: claim, URL, exact quote, location, tag
├── notes/              # research notes
├── lit/                # downloaded PDFs, extracted text, saved abstracts (usually not shared)
├── thresholds.json     # frozen B0 thresholds, with .sha256 and .amendments.jsonl
├── corpus_manifest.md  # topic-scout
├── scout_report.md     # topic-scout
└── brief.md            # research-brief
```

**Evidence tags**

| Tag | Meaning |
|---|---|
| `FT` | The runner matched the sentence, equation or table in the full text, and `quote_check.py` passed |
| `ABS` | Abstract or official landing page only |
| `SEC` | Subagent, search snippet or secondary citation; not verified |
| `FAIL` | Access or tool failure (never evidence of novelty) |

Decisive claims (kill, pass, score) need FT.

**Scoring** ([`rubric.md`](shared/references/rubric.md))

- Novelty 1–5 and feasibility 1–5 are scored separately.
- Verdict classes:
  - **PASS:** novelty ≥ the entry threshold, an FT-verified closest prior, feasibility ≥ 3, and a designed B0.
  - **NEAR-MISS:** novelty = threshold − 1, with a B0 that could flip it.
  - **KILLED:** a named paper, a classical equivalence, or a theory-forced result.
  - **DROPPED:** removed by the scout for an objective reason (exclusion, budget, data, ledger).

**`gate-summary` block**

The report ends with a code block whose info string is `json gate-summary`. The schema is `novelty-gate/v1`; see the example in [`report_template.md`](skills/novelty-gate/references/report_template.md).
- Required keys: `date`, `literature_cutoff`, `entry_threshold`, `verdict` (`pass` / `none`), `candidates[]`, and `coverage[]` (claims × query families A–F).
- Each candidate has `id`, `title`, `claim`, `novelty`, `feasibility`, `status`, `killer_type`, and `closest_prior[]` (`title`, `url`, `tag`, `evidence`).
- PASS and NEAR-MISS candidates also need:
  - `baselines`: `native`, `common_default`, `simplest_key_info`, `equal_compute`;
  - `b0`: `cost`, `primary_endpoint`, `promote_if`, `kill_if`, `inconclusive_if`, `blocked_if`, `known_good`.
- Killed candidates need `failing_gate`. Derivation kills also need `derivation`.

## Scripts

All scripts use only the Python standard library.

| Script | In | What it does |
|---|---|---|
| `guard.py` | all | Blocks use inside autonomous pipelines (exit code 3) |
| `lit_fetch.py` | gate, scout | Literature commands (details below) |
| `quote_check.py` | gate, scout | Checks that each FT quote in `evidence.jsonl` occurs in the cited text, after normalising ligatures, line-break hyphens and whitespace |
| `report_lint.py` | gate, brief | `gate`: summary schema, kill evidence, four baselines, B0 and coverage. `brief`: unfilled fields, placeholders, literature URL count, threshold hash |
| `ledger.py` | all | `validate`, `list`, `check` (near-duplicates), `add` (including `--from-summary`), `update` |
| `freeze.py` | gate, brief | `template`, `freeze` (sha256 of canonical JSON), `verify`, `amend --reason` (logs every change; after results, amendments may only tighten) |
| `corpus_scan.py` | scout | Indexes leads in a corpus |
| `scout_settings.py` | scout | Resolves level, depth, corpus, direction, cutoff and output directory from the request, profile and defaults; prints the settings card |
| `profile_init.py` | all | Creates a profile directory from a few answers (never overwrites without `--force`) |

`lit_fetch.py` commands:
- `arxiv`: date-filtered keyword search. Matching is exact-token.
- `openalex`: relevance search with date filters.
- `citing`: forward citations.
- `resolve`: confirms a citation exists. It queries OpenAlex first, including for arXiv ids; `--no-arxiv` skips the arXiv API.
- `pdf`: downloads a PDF and extracts its text.
- `--save-abstracts DIR`: saves abstracts so ABS quotes can be checked too.
- On HTTP 429 it retries once briefly, then fails fast with a hint.
- OpenAlex has a daily budget: about 100 searches without a key, about ten times more with a free key. Get one at openalex.org (Settings) and `export OPENALEX_API_KEY=...`; it is sent as a header and never printed.

## Validation

```bash
python3 -m unittest discover -s tests -v                  # offline tests for the scripts
LIT_FETCH_LIVE=1 python3 -m unittest discover -s tests    # includes live arXiv/OpenAlex calls
python3 tools/validate_skills.py                          # Agent Skills spec, portability, shared-file sync
```

**Backtests**

[`skills/novelty-gate/evals/`](skills/novelty-gate/evals) holds three public cases with known answers:

| Case | What it checks |
|---|---|
| `kills-test-time-dropout-uncertainty` | Finds the named paper that already contains the idea |
| `flags-theory-forced-rank-metric` | Recognises a theory-forced result |
| `respects-literature-cutoff` | Does not kill with papers published after the cutoff |

- Run them with the skill-creator eval procedure in Claude Code, or from the skill directory with `claude plugin eval . --allow-tools Write,Edit,Bash,WebSearch,WebFetch,Agent,Skill` (Claude Code v2.1.269 or later).
- Each case is a full research session, so expect real time and token cost.

**Private backtests are the most informative.** Build cases from your own past proposals and their real killers, and keep the answers from leaking:
- Agents' automatic memory (for example a per-project memory index) is injected into subagents too. Running from a working directory whose memory records past verdicts breaks blindness, so use a fresh directory or session without such memory.
- When you remove killer names from `lessons.md` for a blind run, replace them with `[redacted]` instead of deleting lines. Deleted lines make lists look truncated.
- Metrics:
  - share of known killers found among the top five priors;
  - number of false PASS verdicts;
  - detection of classical equivalences;
  - time and tokens.
- Compare against a run with no skill and only a long instruction.

## Limitations

- Skills are instructions, so they cannot fully prevent skipped steps. `report_lint.py` and `quote_check.py` check the outputs instead.
- Search quality depends on the host agent's web search and on public indexes:
  - the arXiv API matches exact tokens;
  - OpenAlex may attach citations to either the preprint or the published record;
  - paywalled or bot-protected documents stay FAIL.
- When attack and judgment come from the same model family, blind spots can overlap (see Roadmap).

## Roadmap

- **Cross-model review.** Hand the attack memo or the adjudication to a second model family. This will plug into step 6 of `novelty-gate`.
- **Periodic check.** A scheduled task that checks whether new priors or new public data have appeared for near-miss topics in the ledger.

## Development

- The shared files live in `shared/`. After editing, copy them into each skill with `python3 tools/sync_shared.py` and check with `python3 tools/validate_skills.py`. Never edit the copies inside `skills/` directly.
- Skill files must not reference anything outside their own directory (`../`), so that each skill works when installed alone.
- Keep each `SKILL.md` body under 500 lines and move detail into `references/`.
- To use a working clone directly while developing, link the skills into your agents' skill directories with `tools/install.sh claude-user` or `tools/install.sh codex-user`.
